After readiness, the pipeline reads the design. This page explains the Figma plugin that does it, end to end, and the run on EDS-26 where the plugin was switched off and the pre-flight check still said design: ok.

Checked in Code

The plugin's skill, scripts and manifest were read, along with the extract stage and the pre-flight script that call it. Its five offline test files were run for this page: 221 assertions, 0 failed. The run history comes from the run reports. Paths are relative to plugins/.

The plugin

One operation: fetch_reference

The Figma plugin plays one role in the pipeline: design. Its manifest maps a single operation to a single skill, fetch_reference → fetch-reference. It ships no server of its own.

It wraps Figma's own Claude Code plugin and calls its MCP tools. The skill's allowed-tools lists exactly four of them, plus ToolSearch and Skill. Every decision that can be made from data on disk is made by one of five Python scripts. The model fetches what they name.

  • get_metadata: does the node exist, and what is it

    Name and geometry as XML. Saved verbatim, then handed to the classifier, which decides whether the node is one frame, viewport variants, a page or several frames.

  • get_design_context: the values

    Reference code whose classes carry layout, colour, radius and typography, plus a line naming the styles and variables the node uses. Called once per target.

  • get_variable_defs: the token names

    A flat map of variable name to value, called once for the linked node. An empty map is a normal result: most nodes use no variables.

  • get_screenshot: the reference image

    One per target, sized from the metadata already on disk. Without a size the tool renders the longer edge at 1024 pixels, so a wide frame arrives smaller than it is.

The flow

From a link to files on disk

The input is one line: reference: <figma.com design URL with a node-id>. Everything lands under .ai/figma/.

  1. Check the URL before loading anything. Not a /design/ URL: fail, VALIDATION. No node-id: a question, because a file link does not say which frame is meant.
  2. Load the four tools. Nothing resolves: the Figma plugin is not installed or not enabled, fail PERMANENT. Only authenticate resolves: installed but signed out, fail PERMANENT with a fixed sentence telling the user how to sign in.
  3. Fetch metadata and run classify-node.py. Its first line is the class. The skill never re-decides it from names, sizes or the ticket.
  4. For viewport variants, viewports.py plan prints one target per variant, widest first. The skill fetches exactly those, no more, no fewer.
  5. Per target, fetch the design context and hand the code straight to fetch-assets.py on standard input. It downloads every image and icon, names each format from its bytes and writes the code with local paths.
  6. Fetch the variables once, then one screenshot per target, sized by screenshot-size.py, which also records whether the render came back smaller than the node.
  7. Write <file>-<node>.json with the reference, geometry, variables, design context, screenshots, assets and, for variants, the list of viewports. Report pass with every file written.

One link, four meanings

The model never picks a frame

A Figma link names one node. Behind it can be one frame, several widths of the same design, a whole page, or unrelated frames. classify-node.py decides which, from the metadata alone.

singleOne target

The node itself is fetched.

variantsEvery width, widest first

Every frame-like child belongs to one group of two or more viewport variants.

pageA question

The node is a page. Every frame on it is listed as an option.

multi-frameA question

A section, or variants mixed with other frames. Every frame is listed as an option.

# classify-node.py: what makes a variant
name:pattern   "X / Desktop", "Hero - Mobile",
               "Desktop View", "@mobile"
name:keyword   desktop, mobile, tablet,
               responsive, phone, web
name:width     1440, 1280, 1024, 768,
               375, 390, 414
size           same-name siblings, one wider
               than 900 and one narrower than 500

The rule that matched is written next to every child, so a run can be audited afterwards.

A question lists every candidate with its node id, in document order. None is dropped, reordered or marked as preferred, not even one whose name matches the ticket. A frame chosen by name would be a guess that looks like a fetch.

Failures

Every failure carries its class

The class is read from what the tool actually returned, never from which call it was. The stage that called the plugin decides what to do with it.

  • TRANSIENT: retried twice

    A rate limit, a quota, a plan's call limit, a timeout, or a failed asset download. Back off 2 seconds, then 4. Then fail.

  • VALIDATION: the request is wrong

    The file or node was not found, or the URL is not a supported design URL. Re-running it unchanged cannot succeed.

  • PERMANENT: the provider cannot run here

    Not installed, not enabled, not signed in, no access, or anything unrecognised. An unknown error is not evidence that retrying is safe.

  • Sign-in is reported, never started

    The plugin never calls authenticate. An unattended run has nobody to open the link, and would stall instead of failing.

TRANSIENT or PERMANENT

The provider failed

  • The reference itself is not in question.
  • If the ticket has a declared reference image, extract uses it.
  • It returns warn, never pass, with has_values: false.
VALIDATION

The request is wrong

  • The ticket named something that does not exist.
  • Substituting another artifact would answer a question nobody asked.
  • Extract fails, attachment or not.

The rule, as the extract skill states it: TRANSIENT and PERMANENT describe the provider and permit substitution. VALIDATION describes the request and forbids it.

The run

Three runs on EDS-26

The ticket is a logo cloud block with three Figma links: desktop, tablet and mobile. It took three runs to deliver it.

  • Run 1

    The Figma tools were not available: PERMANENT: figma plugin MCP tools not available. Extract fell back to the attached image with warn and has_values: false. The plan gate failed later for a separate reason: the ticket asked for a comparison with three captures, and extract reads one reference. That part is post 8.

  • Run 2

    Same failure, same fallback. The run went through conventions, serve and baseline on a picture without sizes, until the prototype refused to set fixed sizes it had no values for. Pre-flight had printed design: ok both times.

  • Why pre-flight said ok

    check-preflight.sh checks that every role the project needs has a pack whose manifest validates. Its own header says what it is not: never a runtime health check against a live tool. The Figma pack's manifest was fine. The Figma plugin it wraps was disabled in /plugin.

  • Run 3

    The plugin was enabled and signed in, and the ticket's criteria had been rewritten with measured sizes. Extract passed with has_values=true, and the run delivered pull request #246.

What it doesn't solve

The fixes are in the run, not yet in the code

Enabling a plugin and rewriting a ticket got EDS-26 delivered. Three things the runs exposed are still open.

  • Pre-flight

    It still trusts declarations. A live check that the design tools answer before the run starts is designed, not built yet.

  • Several links

    resolve-design-source.py takes the first Figma link in the ticket. The others are ignored without a message. The variant mechanism above only helps when one node holds every width.

  • The file's structure

    In this Figma file, Desktop, Tablet and Mobile are full page frames, and the block sits inside each one. No single node holds the three widths, so the classifier sees each linked node as single. Finding the counterparts by their name path is planned, not decided.
