Delivery Factory · Part 3 · Readiness

Readable is not reachable.

The readiness gate passed EDS-26, a logo block with a Figma design. It was right to: the ticket had everything the gate checks. The run still could not deliver it, because two criteria pointed at designs the pipeline never opens.

Checked in Code

The gate and the design stage were read in their scripts, skills and manifests, not only in a README. The criteria come from the ticket's own git history, before and after. Paths are relative to plugins/. The delivered change is pull request #246.

The gate

A script answers "can this be worked at all"

Readiness runs on every ticket, right after intake. It has no model: every criterion is a comparison between a fact record and the platform's manifest.

# eds/pack.yaml
readiness_criteria:
  Story:
    require: [has_description,
              has_acceptance_criteria,
              reproduction_content_ok]
  Bug:
    require: [has_description,
              has_reproduction_url,
              has_reproduction_steps,
              reproduction_content_ok]

Intake writes the facts first. "Has acceptance criteria" is a literal match: the Jira manifest names the headings it accepts, Acceptance Criteria or AC. No model reads the ticket and forms an opinion, so two runs on the same ticket get the same facts.

Then check-readiness-criteria.sh compares the two files. The answer is pass or fail. There is no warn, no "ready, with reservations".

  • A ticket type with no declared criteria fails

    It never falls back to another type's rules and never guesses.

  • A field the record could not determine never counts as met

    Absent or null is not true.

  • A check that could not run is a fail, not a pass

    The script exits 2 on a usage error, and the stage reports it as a fail of its own kind. The skill gives the reason: treating "did not run" as "passed" is how a gate becomes decorative.

  • Two fixed rules, whatever the type

    A ticket that asks for a visual change with no design attached fails. So does one that compares against a before-state no stage can capture.

## Result
verdict: pass
summary: Item type Story: its declared
  readiness criteria all hold (3 fields checked).
artifacts: []
next_action: none

What the gate returned for EDS-26. A failure names the exact field instead, for example item_type 'Story' requires 'has_acceptance_criteria' to be true, found false.

One link

The design stage takes one reference

The ticket gave three Figma links: desktop, tablet and mobile. The stage that reads the design is built around a single one.

# eds/skills/eds-extract: decision= lines
url        one design-tool URL,
           reference=<url>
image      no URL, images resolved
           to one reference
ambiguous  no URL, images did not
           resolve: ask a question
missing    a design was called for,
           none found: fail

A script, resolve-design-source.py, makes this decision, not the model. When the ticket has a URL, the result carries one reference=, and the skill says a URL never arrives as ambiguous.

The question path exists only for images without a URL. Several Figma links do not trigger it. On EDS-26 the stage reported "Figma node Logo Row, 1200x84", the desktop design, and nothing about the other two.

The old ticket said so itself: the tablet and mobile captures were what AC-4, AC-5 and AC-7 were compared against below the breakpoint.

The rewrite

From "as shown" to a number

The gate stayed as it was. The ticket changed: every size and spacing was measured on the design nodes and written into the criteria. 13 criteria became 16.

Before · 13 criteria

Points at a picture

  • AC-4: Below the widest project breakpoint, the logos wrap into as many rows as the viewport needs, as laid out in the tablet and mobile design references.
  • AC-5: A row that is not full renders centred, as the tablet design reference shows for its second row.
  • AC-7: Every logo renders inside a cell of the size and spacing shown in the design reference at the matching width.
After · 16 criteria

Carries a number

  • AC-4: At a viewport 720 wide, the first row holds four logos.
  • AC-5: At a viewport 720 wide, the second row holds two logos.
  • AC-8: Each logo sits in a cell 150 by 82 pixels, within 1 pixel, at viewports 375, 720 and 1200 wide.
  • AC-9: Adjacent cells in a row are 40 pixels apart, within 1 pixel.
  • AC-10: Adjacent rows are 20 pixels apart, within 1 pixel, at viewports 375 and 720 wide.

The rewritten ticket names the one place the design disagrees with itself: the first five desktop cells measure 154 by 84, the sixth 150 by 82. It takes 150 by 82 as intended and says why. That is a decision a human made once, in the ticket, instead of one the pipeline would have made silently in every run.

The same ticket, rewritten, went through the route and was delivered as pull request #246: two files, logo-cloud.js and logo-cloud.css.

What it doesn't solve

Readiness still checks presence

The fix lives in the ticket, not in the gate. The next ticket written "as shown in the design" will pass readiness the same way.

  • The gap

    Readiness checks that criteria exist under the right heading. It does not check that the pipeline can reach what they point at, and it is not allowed to re-read the ticket's text to find out.

  • Numbers find new problems

    Even the rewritten ticket was not clean. At 375 wide the page's content box is 327 px, while two 150 px cells and a 40 px gap need 340. The plan gate returned warn for that. The delivered CSS answers it with margin-inline: -24px below the breakpoint. With "as shown in the design" the conflict would not have been measurable at all.
